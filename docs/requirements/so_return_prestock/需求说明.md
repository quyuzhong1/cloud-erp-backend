## 一、背景与目标

### 1.1 业务背景

海外仓或物流商在收到退货包裹后，会生成退货入库单（`so_return_instock`）并推送到 ERP 系统。然而，该入库单中的物品到底属于哪个店铺、哪个销售订单、哪个售后单，往往在入库单到达时并不明确，需要运营人员事后手动进行关联匹配。

预入库单（`so_return_prestock`）作为一个**中间暂存载体**，用于承接"已收货但尚未完全关联到业务单据"的退货物品信息，帮助运营人员统一管理关联进度。

### 1.2 核心目标

- 提供统一视图，让运营人员清晰看到哪些退货已关联、哪些未关联、哪些部分关联
- 支持运营人员对未关联的预入库单数据进行**关联售后单**、**关联店铺**操作
- 支持手动录入预入库单（不依赖外部推送）

## 二、核心业务规则

### 2.1 数量拆分规则（重要）

> 这是该业务最核心的设计约束，开发必须充分理解。

一条预入库单详情记录（某个 SKU + 数量）在关联操作过程中**可以被拆分为多条**：

**场景示例**：
```
初始状态：
  详情行 A：SKU=123456，数量=10，关联状态=未关联

拆分后（运营关联操作触发）：
  详情行 A1：SKU=123456，数量=3，店铺=A，销售单=SO-001，关联状态=已关联
  详情行 A2：SKU=123456，数量=4，店铺=B，销售单=SO-002，关联状态=已关联
  详情行 A3：SKU=123456，数量=3，关联状态=未关联
```

**拆分触发时机**：
- 运营执行【关联售后单】操作，且本次关联数量小于当前行数量时
- 运营执行【关联店铺】操作，且本次关联数量小于当前行数量时

**拆分约束**：
- 拆分后各行数量之和 = 原行数量
- 原行数量不得减少（只能被拆分，不能直接修改数量字段）
- 已关联的行不可再被拆分关联（需先解除关联）
- TODO：明确"部分关联"场景下是否允许对已关联的子行再次关联

### 2.2 主表关联状态联动规则

主表的【关联状态】由其所有详情行的状态自动汇总决定：

| 详情行状态分布 | 主表关联状态 |
|---|---|
| 全部为【未关联】 | 未关联 |
| 全部为【已关联】 | 已关联 |
| 存在已关联和未关联混合 | 部分关联 |

### 2.3 一单一物流单号约束

- 一条预入库单对应且仅对应**一个**退货物流单号
- 同一个物流单号下可以有多个 SKU 的多条详情记录

    inventory_org_id      VARCHAR(32)      NOT NULL DEFAULT '',   -- 库存组织 ID（对齐：so_return_instock.inventory_org_id）
    inventory_org_name    VARCHAR(100)     NOT NULL DEFAULT '',   -- 库存组织名称

### 6.1 由退货入库单表单发起创建（新增能力）

**背景**：新增/修改退货入库单页面下方新增【预入库】按钮。当运营尚不清楚"退货客户"归属时，填写完退货物流单号、产品明细等信息后，可点击【预入库】直接将当前表单数据存入预入库单，而不是勉强指定一个客户创建退货入库单。

**触发前提**（后端强制校验，不满足则报错）：
- 退货客户（`customerId`）必须为空；若已填写客户，说明客户信息已明确，应直接走【新增/修改退货入库单】的正常保存流程，创建预入库单没有意义
- 退货物流单号（`returnLogisticCode`）必须非空；预入库单以物流单号作为唯一键（见 3.1 节唯一索引）

**字段映射说明**：
- `type`、`returnLogisticCode` 直接取自退货入库单表单
- `warehouseId` 取自退货入库单表单的仓库字段，反查仓库所属库存组织，写入预入库单 `inventory_org_id`/`inventory_org_name`、`warehouse_id`/`warehouse_name`
- 明细行 `skuId`/`skuNo`/退货数量（`realQty`）/实际收货数量（`receivedQty`）/备注 直接取自退货入库单明细；`productName`/`productImageUrl`/`ean` 通过 SKU ID 批量反查补齐（退货入库单明细本身不落这三个字段）
- `source_type` 固定写入 `MANUAL`（人工在退货入库单表单发起，非海外仓自动拉取）
- 原表单的退货订单号（`soReturnCode`，如有）写入预入库单 `remark`，便于运营事后追溯

**库存联动（新增行为）**：预入库单本身不直接触发库存变动；`/saveFromInstockAdd`、`/saveFromInstockUpdate` 在成功创建预入库单后，会在同一事务内**同时生成并自动审核一张"其它入库单"**（`erp-model-wms` 的 `OtherInstockEntity`，类型固定为 `InstockTypeEnum.THREE_NO_PRODUCT_PRE_INSTOCK` 三无退货预入库），走 `OtherInstockService.addAndApprove(entity, false)` 完成新增、提交、审核，并通过 `InventoryTransCoreService` 增加对应仓库/SKU 的库存，使预入库真正反映到库存数据上：
- `billDate` 取预入库单的实际收货时间/签收时间（`received_time`）
- `inventoryDirection` 固定为 `InventoryDirectionEnum.ORDINARY`（正向入库，参照旺店通预入库范式）
- `warehouseId`/`warehouseName`、`orgId`/`orgName` 复用预入库单已解析出的仓库、库存组织信息
- `deptId`/`deptName` 取默认仓储部门（`WmsConstant.DEFAULT_WAREHOUSING_DEPT_ID`，与旺店通预入库共用同一兜底部门，如后续该部门不适用于此场景需业务另行指定）
- `sourceType` 写入新增枚举 `SourceTypeEnum.SO_RETURN_PRESTOCK`，`sourceId`/`sourceCode` 回指本次新建的预入库单
- 明细行按预入库单详情逐条生成，`actualQty` 取退货数量，`sourceDetailId` 回指预入库单详情行 ID
- 该生成过程与退货入库单原有的审核增库存入口完全独立，互不影响；若生成/审核失败，异常会回滚本次预入库单的创建，不会遗留"预入库单已建但库存未增加"的不一致状态

## 十三、关联表最终新增字段

> 本需求同批在已有表上新增的字段（预入库主表/明细见第三章 `CREATE TABLE`）。下列 SQL 为**首次补列**脚本，无 RENAME/DROP。

| 表 | 字段 | 说明 |
|---|---|---|
| `so_return_instock` | `dict_platform` | 平台字典值；B2C 取售后单平台，否则取客户归属平台，可能为空 |
| `so_return_instock_detail` | `remain_should_qty` | 剩余应退货数量 = 应退数量 − 历史已入库实退累计（含本次）；无法计算时为空 |
| `so_return_instock_detail` | `prestock_detail_id` | 来源预入库单明细 ID；仅 `sourceType=soReturnPrestock` 时有值；与 `source_detail_id`（签收单明细）语义分离 |
| `other_instock_detail` | `prestock_detail_id` | 同上，预入库生成其它入库单时回指预入库明细 |
| `so_return_prestock_detail` | `defective_product_flag` | 是否不良品；海外仓拉取透传，拆行与关联下游时保留 |
| `other_instock_detail` | `defective_product_flag` | 是否不良品；预入库联动生成其它入库时透传，审核入账按不良品写入库存状态 |

```sql

ALTER TABLE so_return_instock ADD COLUMN IF NOT EXISTS dict_platform VARCHAR(64) NOT NULL DEFAULT '';
COMMENT ON COLUMN so_return_instock.dict_platform IS '平台字典值：B2C取售后单平台，否则取客户归属平台，可能为空';

-- so_return_instock_detail：剩余应退 + 预入库明细回指
ALTER TABLE so_return_instock_detail ADD COLUMN IF NOT EXISTS remain_should_qty INTEGER;
COMMENT ON COLUMN so_return_instock_detail.remain_should_qty IS '剩余应退货数量 = 应退数量 - 历史已入库实退数量累计（含本次）';

ALTER TABLE so_return_instock_detail ADD COLUMN IF NOT EXISTS prestock_detail_id VARCHAR(32) NOT NULL DEFAULT '';
COMMENT ON COLUMN so_return_instock_detail.prestock_detail_id IS '来源预入库单明细ID（so_return_prestock_detail.id），仅 sourceType=soReturnPrestock 时有值';

-- other_instock_detail：预入库明细回指
ALTER TABLE other_instock_detail ADD COLUMN IF NOT EXISTS prestock_detail_id VARCHAR(32) NOT NULL DEFAULT '';
COMMENT ON COLUMN other_instock_detail.prestock_detail_id IS '来源预入库单明细ID（so_return_prestock_detail.id），仅 sourceType=soReturnPrestock 时有值';

-- 预入库明细 / 其他入库明细：不良品标识
ALTER TABLE so_return_prestock_detail ADD COLUMN IF NOT EXISTS defective_product_flag BOOLEAN NOT NULL DEFAULT FALSE;
COMMENT ON COLUMN so_return_prestock_detail.defective_product_flag IS '是否不良品（true=不良品，false=良品/可用）';

ALTER TABLE other_instock_detail ADD COLUMN IF NOT EXISTS defective_product_flag BOOLEAN NOT NULL DEFAULT FALSE;
COMMENT ON COLUMN other_instock_detail.defective_product_flag IS '是否不良品（true=不良品，false=良品/可用）';
```

### 13.1 `dict_platform` 写入规则

- **取值**：`type = B2C` 时取关联 `SoB2cReturnEntity.dictPlatform`；否则取客户 `CustomerInfoEntity.platformType`；都取不到则为空
- **时机**：退货入库单新增/修改时落库；查询优先读库内值，历史空值可按原逻辑临时计算兜底

### 13.2 `remain_should_qty` 写入规则

- **口径**：权威应退数量（B2B：`so_return_detail.return_qty`；B2C：`so_b2c_return_detail.return_qty`）− 历史已入库实退累计（含本次）
- **时机**：`addB2b` / `addB2c` / `notReturnOrderAdd` / `updateB2b` / `updateB2c` / `notReturnOrderUpdate` 在超额校验后写入
- **为空**：未关联退货单/售后单或无法确定应退数量时不写

### 13.3 `prestock_detail_id` 写入规则

- 预入库认领/关联店铺生成退货入库单或其它入库单明细时写入对应预入库明细 `id`
- 编辑退货入库单时：入参非空才覆盖；空值/缺失不覆盖已有关联，避免误清空

### 13.4 `defective_product_flag` 写入规则

- **取值**：海外仓 MQ `PlatformReturnInstockDTO.Detail.defectiveProductFlag`；`true`=不良品，`false`/空=良品
- **时机**：创建预入库明细时落库；拆行复制原行值；联动生成其他入库明细、关联生成退货入库明细时透传
- **库存**：其他入库审核入账时，若明细为不良品则写入 `InventoryStatusEnum.DEFECTIVE_PRODUCT`（与退货入库一致）
