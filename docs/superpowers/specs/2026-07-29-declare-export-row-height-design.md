# 报关单导出明细行自适应行高设计

## 目标

优化 `TmsDeclareBillServiceImpl#exportDeclare` 的 sheet0 报关单明细行展示：根据每条 `ExportDTO.productDetailList` 明细的实际内容和模板列宽自动设置行高，避免长文本被截断，同时保持短文本的现有模板排版和导出业务口径不变。

## 范围与兼容约束

- 仅处理多 sheet 导出结果的 sheet0（报关单 sheet）明细区。
- 明细模板首行是 Excel 第 18 行，POI 行下标为 17；`ExportDTO.productDetailList` 的每项对应一条明细行。
- Excel 第 18 行的原始行高是所有明细行的最小行高；自适应计算结果不得使行高低于该值。
- 允许行高按实际内容自然增大，不设置额外最大行高，避免内容截断。
- 合同、发票、装箱单、装箱明细等其他 sheet 的行高保持现有行为。
- 保持现有接口路径、响应格式、状态过滤、字段值、明细顺序、合并区域和单条/多条产物形态兼容。
- 单条 xlsx 和多条 ZIP 内的每个 xlsx 都复用同一套 sheet0 后处理逻辑。
- 不新增数据库查询、Feign 调用或第三方依赖。

## 现有链路

1. `exportDeclare` 查询导出主表数据和明细。
2. `fillExport` 补全报关单主表、明细字典名称、金额和合计字段。
3. `fillExportMulti` 批量补全合同、发票、装箱单和装箱明细 sheet 数据。
4. EasyExcel 使用多 sheet 模板填充数据。
5. `normalizeDeclareSheet` 使用 Apache POI 对内存中的 xlsx 进行 sheet0 明细空白行清理、合并区域修复和最终写回。

行高处理放在第 5 步，因为该阶段已经有最终的 workbook、实际填充后的文本和模板样式，不需要再打开模板或增加一次 xlsx 解析。

## 设计方案

### 1. 在 POI 后处理阶段统一设置行高

扩展 `normalizeDeclareSheet` 的 sheet0 处理流程：

1. 计算并清理 EasyExcel 生成的多余空白明细样式行。
2. 修复 sheet0 明细行的合并区域。
3. 根据第 18 行模板行高和明细行实际内容计算每一条明细行行高。
4. 设置所有明细行的最终行高。
5. 继续现有 workbook 写回流程。

对 `detailSize <= 0` 不处理明细行；对 `detailSize == 1` 也设置首条明细行行高，但不改变现有仅多条明细时才执行的合并修复条件。

### 2. 行高计算输入

使用 sheet0 第 18 行的模板信息作为基准：

- 默认行高：`templateRow.getHeight()`；若模板行高未显式设置，则使用 `sheet.getDefaultRowHeight()`。
- 行高基准：沿用模板第 18 行的原始行高，不重新测量字体像素高度；这样可以保持模板字体、字号和垂直对齐效果一致。
- 文本内容：读取明细行中模板有占位符的实际单元格内容，而不是扫描整张 sheet 的所有单元格。
- 显示宽度：读取列宽；若占位符所在位置属于横向合并区域，则使用该合并区域包含列的总宽度，并扣除少量单元格边距。

### 3. 明细占位字段与列区域

行高计算只关注第 18 行模板中有明细占位符的单元格，并在代码中集中维护占位字段到列区域的映射，避免每次导出扫描模板 XML 或全表字符串：

- 普通单元格：按其单列宽度计算。
- 横向合并字段：按合并区域总宽度计算，例如申报要素、征免等字段。
- 需要覆盖截图中展示的所有明细占位字段，包括商品编号、商品名称、申报要素、单位、单价、数量、总价、币制、原产国、最终目的国、境内货源地、征免、SKU、业务单号等。

字段映射使用与 `ExportProductDetail` 属性一致的 getter/value 读取方式。空值不增加行数，但仍保留模板默认行高。

### 4. 文本换行估算

不使用 AWT `FontMetrics` 或逐字符图形测量，避免服务器无头环境问题和额外 CPU 开销；采用确定性的 Excel 列宽近似算法：

- 先按 `\\r\\n`、`\\n`、`\\r` 拆分显式换行段；至少按 1 行计算。
- 中文、全角字符及其他宽字符按约 2 个 ASCII 字符宽度估算。
- ASCII 英文、数字和常见符号按约 1 个字符宽度估算。
- 对每个显式换行段按可用列宽累计字符宽度，向上取整得到自动换行行数。
- 当前字段需要的行数取所有显式换行段行数之和。
- 当前明细行需要的行数取该行所有占位字段需要行数的最大值。
- 最终行高按模板默认行高乘以需要行数计算，并与默认行高取最大值。

算法目标是与 Excel 的 `wrapText` 展示行为保持稳定、保守的近似，宁可适度增加高度，也不因估算偏小导致内容截断。

### 5. 合并区域处理

行高设置在合并区域修复之后执行。对于每个明细行：

- 通过预构建的列区间映射识别横向合并字段。
- 同一个合并区域只计算一次，避免区域内多个物理单元格重复计数。
- 不修改合并区域本身；只设置该行的 `height`。
- 现有 `mergeDeclareDetailRows`、`removeBlankDeclareDetailRows` 和边框处理逻辑保持不变。

### 6. 性能优化

行高计算只增加一次内存中的 sheet0 轻量扫描，复杂度约为明细行数乘以已知明细字段数，不涉及远程调用。

同时在 `fillExport` 中做与本次导出直接相关的低风险索引优化：

- 明细列表按 `mainId` 一次性分组，替代每张报关单对完整明细列表重复过滤。
- 物流单按出库单号预构建 Map，替代每张报关单对完整物流列表重复 stream/filter。
- 报关字典和申报单位字典预构建 Map，替代每条主表/明细重复 stream/filter。
- 保持重复 key 的原有首值语义，不改变缺失值回退行为。

不改变既有批量 Feign 查询结构，且不引入并行处理，避免多条导出共享状态和响应顺序问题。

## 异常与回退

- 模板第 18 行缺失时，使用 sheet 默认行高作为下限；不会因无法读取模板基准而把行高设为更小值。
- 单元格、样式、字体或列宽信息缺失时，使用保守默认值继续计算。
- 单个字段值为空、明细对象为空或明细集合为空时，不抛异常。
- 若 POI 后处理整体失败，沿用当前 `FILE_EXPORT_FAILED` 处理，不输出不完整文件。

## 验证方案

### 单元测试/辅助测试

覆盖行高计算辅助逻辑：

- 空值和短文本保持默认行高。
- 中文长文本按列宽增高。
- 英文/数字长文本按列宽增高。
- 中英文混合文本不会低估所需高度。
- 显式换行增加行数。
- 横向合并区域使用合并后的总宽度，而不是左上角单列宽度。
- 多个字段取最大行数而不是累加字段高度。
- 任意计算结果不低于模板第 18 行高度。

### 模块验证

优先执行：

```powershell
mvn -pl erp-server/erp-server-tms -am compile
```

若已有可运行的 TMS 测试，再执行：

```powershell
mvn -pl erp-server/erp-server-tms -am test
```

使用实际模板验证单条和多条导出：检查 sheet0 明细文本显示、行高、合并区域和其他 sheet 行高均符合设计。若外部 Nacos、Redis、PostgreSQL 或 Feign 环境不可用，说明未验证的运行时风险。

## 验收标准

- sheet0 每条明细行最终行高不少于模板第 18 行原始行高。
- 长文本和显式换行内容可完整显示，不被明细行裁切。
- 横向合并字段按合并后的显示宽度估算。
- 只改变 sheet0 明细行行高。
- 单条 xlsx 与多条 ZIP 导出结果一致。
- 不增加数据库/Feign 调用次数。
- `fillExport` 索引优化后导出字段、顺序、空值回退和合计值保持一致。
- 模块编译通过；可执行测试通过或明确记录环境限制。
